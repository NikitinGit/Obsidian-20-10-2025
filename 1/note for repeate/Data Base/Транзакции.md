>[!question]- Session Metrics
> Статистика Hibernate **по одной сессии** (persistence context), печатается при её закрытии. Включается: `hibernate.generate_statistics=true` + логгер `StatisticalLoggingSessionEventListener=INFO`. **Один блок = итог жизни одной сессии** (поэтому у «без @Transactional» при OSIV=false их ДВА — две сессии).
> Единица — **наносекунды**: `1 000 000 ns = 1 ms`.
>
> Построчно:
> - `acquiring N JDBC connections` — время получить соединение из пула (обычно 1 на сессию).
> - `releasing N JDBC connections` — время вернуть соединение в пул.
> - `preparing N JDBC statements` — время подготовки `PreparedStatement` (парсинг SQL, prepare).
> - **`executing N JDBC statements`** — время выполнения отдельных SQL. **N = сколько запросов ушло в БД** (ключевой индикатор: ждали 2, а тут 50 → N+1).
> - `executing N JDBC batches` — время на батчи (пакетные insert/update). 0 = батчинг не использовался.
> - `L2C puts / hits / misses` — активность кеша **2-го уровня** (0 = L2 не подключён).
> - **`flushes (flushing X entities …)`** — время flush + сколько сущностей реально записано (dirty checking). **0 flushes = ничего не писали**; `1 flush, 1 entity` = был `UPDATE`.
> - `pre-partial-flushes` / `partial-flushes` — частичные сбросы PC перед запросом (оптимизация), обычно 0.
>
> Как читать «на глаз»:
> - `executing N statements` большое → **N+1** (ищи забытый `JOIN FETCH`/`@EntityGraph`);
> - `flushes … >0 entities` → были **записи** (dirty checking что-то сохранил);
> - `acquiring connections` большое → **contention пула**.
>Проверено на нашем демо (readOnly true/false/без tx):
>
> 
> | Сценарий | `executing N` | `flushes / entities` |
> |---|---|---|
> | `readOnly=true` | 1 (`select`) | 0 / 0 |
> | `readOnly=false` | 2 (`select`+`update`) | 1 / 1 ← dirty checking записал |
> | без `@Transactional` (OSIV off) | по 1 в ДВУХ блоках | 0 / 0 |
>
> Есть ещё **глобальная** агрегированная статистика — `SessionFactory.getStatistics()` (за всё время, удобно через Micrometer/Actuator). `generate_statistics=true` даёт overhead — включать точечно для диагностики (обычно ловят N+1), не держать в проде постоянно.

>[!question]- Dirty checking
>проверка грязных сущностей - тех, начальный SNAPSHOT которых изменился
>```
>Battle b = repo.findById(1L).get(); 
>  // (1) Hibernate грузит сущность И сохраняет SNAPSHOT (слепок полей на момент загрузки):
>  //     snapshot = {idBattle=1, sectionNumber=25}
>  b.setSectionNumber(26);
>  // (2) меняем поле В ПАМЯТИ. b теперь "грязный": текущее (26) ≠ snapshot (25).
>  //     Но в БД пока ничего не ушло, save() мы НЕ звали.
>  // (3) конец @Transactional-метода → FLUSH: Hibernate проходит по всем managed-сущностям и СРАВНИВАЕТ  текущие поля со snapshot'ом: 
> → генерирует и выполняет:  update battles set section_number=26 where battle_id=1      
>```

>[!question]- @Transactional(readOnly = true)
>1. отключает сохранение через сеттеры сущности  (dirty checking + авто-flush) - battle.setSectionNumber(25); - sql запрос  update battles set ... не вызывается
>2. battlesRepository.updateBattle(battleId); вызывает исключение ```Connection is read-only. Queries leading to data modification are not allowed```
>3. экономия памяти/CPU на больших выборках - при чтении read-only сущностей Hibernate не создаёт snapshot'ы (per-entity работа на гидрации)
>4. стртаховка от случайного сохраненения  - явно указывается что только для чтения
>5. проблему N + 1 не снимает 
>6. гарантировано второй select читает из PC (даже если OSIV=true)
>7. Для всех выбранных сущностей создаются снепшоты в ОЗУ; на flush (обычно в конце транзакции) CPU проходит dirty checking'ом, сравнивает каждую сущность со снепшотом, и для отличающихся выполняет UPDATE. При readOnly = true снепшоты не создаются и этот проход не выполняется — записи  нет.

>[!question]- bulk-запрос
>массовый (оптовый) запрос на изменение нескольких строк - 
>```
>UPDATE Battle SET active = false WHERE tournamentId = 5   -- одним стейтментом обновит хоть 1000 строк
>```
> Ключевые свойства bulk-операции (важно понимать отличие от ORM-подхода):
>  обходит persistence context / кеш 1-го уровня — Hibernate не знает, что в памяти уже загруженные Battle теперь устарели (stale). После bulk-UPDATE часто нужно em.clear()/refresh(), иначе будете работать с протухшими данными;                                                                                
>  - не вызывает lifecycle-колбэки (@PreUpdate/@PostUpdate) и не инкрементит @Version автоматически; 
>  - не делает dirty checking — просто отправляет ваш SQL как есть; 
>  - требует транзакцию (executeUpdate).

>[!question]- Транзакция всегда занимает строго один поток?
> Да — в классической, синхронной модели Spring (`@Transactional` + JDBC/JPA). `TransactionSynchronizationManager` хранит состояние транзакции (соединение, имя, флаг активности) в полях `NamedThreadLocal` — а `ThreadLocal` физически не виден с другого потока, значит транзакция не может "перепрыгнуть" на другой поток посреди выполнения, только начаться и закончиться на одном и том же.
>
> Это не только ограничение Spring, но и объективная причина: `java.sql.Connection` (то, что реально "внутри" транзакции) не thread-safe и не рассчитан на использование из нескольких потоков одновременно — передавать транзакцию другому потоку было бы небезопасно уже на уровне JDBC.
>
> Проверено эмпирически (проект SpringBeans): транзакция, открытая на потоке `main`, при вызове `@Async`-метода (который выполняется на новом потоке из пула, например `task-2`) **не наследуется** — внутри `@Async`-метода `@Transactional` открывает совершенно новую, независимую транзакцию (другое имя, которое возвращает `TransactionSynchronizationManager` → `getCurrentTransactionName()`). Причина: `AsyncAnnotationAdvisor` в цепочке интерцепторов стоит снаружи `TransactionInterceptor`, поэтому переключение потока происходит **раньше**, чем транзакционный advice успевает сработать — к моменту открытия транзакции мы уже на другом потоке, где старой транзакции просто не видно.
>
> Практические следствия:
> - откат транзакции "вызывающей стороны" **не откатывает** независимую транзакцию, уже выполненную/закоммиченную внутри `@Async`-метода на другом потоке — риск рассинхронизации данных;
> - `@Async`-метод с `void`-возвратом — fire-and-forget: вызывающий код возвращается **до** того, как асинхронный метод вообще начал выполняться, и исключение внутри него никогда не долетит до вызывающего кода (только `AsyncUncaughtExceptionHandler`, если настроен).
>
> **Исключение**: реактивный стек Spring (`ReactiveTransactionManager`, WebFlux + R2DBC) привязывает транзакцию не к `ThreadLocal`, а к Reactor `Context`, который передаётся по цепочке операторов независимо от того, какой event-loop поток исполняет конкретный шаг — там одна и та же логическая транзакция вполне может физически выполняться на разных потоках за свою жизнь. Именно поэтому реактивному стеку понадобился отдельный механизм трекинга транзакций.

>[!question]- для каждого метода помеченного @Async вызывается свой поток для транзакции ?
> Нет, не "свой" (не выделенный, не уникальный) — потоки берутся из пула (`ThreadPoolTaskExecutor`, у Spring Boot по умолчанию `corePoolSize = 8`) и **переиспользуются**. `@Async` не создаёт `Thread` на каждый вызов — он отправляет задачу в `Executor`.
>
> Проверено эмпирически (10 последовательных вызовов одного `@Async`-метода):
> ```
> task-1, task-2, task-3, task-4, task-5, task-6, task-7, task-8,   // первые 8 — новые потоки (corePoolSize)
> task-1, task-2, ...                                                // дальше — переиспользование тех же потоков пула
> ```
>
> На транзакцию переиспользование потока **не влияет** — на 9-м вызове `task-1` используется повторно, но транзакция всё равно каждый раз новая и чистая. Причина: `TransactionInterceptor` в `finally`-блоке всегда вызывает очистку ресурсов (метод `TransactionSynchronizationManager` → `clear()`, unbind) по завершении **каждой** транзакции — независимо от того, будет ли этот физический поток потом переиспользован для другого вызова.
>
> Правильная формулировка: не "свой поток на метод", а **"своя транзакция на каждый вызов, независимо от того, какой физический поток пул ей выделит"**.
